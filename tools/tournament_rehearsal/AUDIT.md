# Tournament audit — 29 October 2026

Scope: the released `/tournament` surface and native tournament creation, persistence, entry conditions, pairing, browser play, score sheets, standings, completion and recovery. Swiss and simultaneous exhibitions remain deferred under the repository instructions. Existing unrelated work in this checkout was preserved.

## Findings and fixes

| Area                         | Defect                                                                                                                                                                                         | Correction                                                                                                                                                                                                                                                                                                               |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Variants                     | The creation form mixed Jieqi with Standard repetition policies and only offered Standard as a variant. Pairing always constructed a Standard board.                                           | Native `GameVariant` owns available variants, supported policies, custom-position support and initial game construction. Tournament forms derive choices from that registry; Standard alone offers Tiantian/Unrestricted. Jieqi receives a hidden-piece game. Mini Xiangqi appears automatically from the same registry. |
| Metadata and ranks           | Tournament storage, display and player snapshots did not consistently preserve the native variant.                                                                                             | Persist native tournament variant, use the variant's rank track on join, and expose consistent names and native metadata through list/detail/API views. Standard remains the existing default for ordinary stored tournaments.                                                                                           |
| Entry conditions             | Loading a scheduled tournament that had not started discarded its stored entry restrictions.                                                                                                   | Preserve organizer conditions during BSON decoding; regression coverage includes a scheduled allow-list event.                                                                                                                                                                                                           |
| Editing                      | Clock components, position and game semantics could change after registration; scoring options could change during play. A stale form snapshot could overwrite concurrent state.               | Lock game settings once a participant joins; lock scoring after start; re-read and transform current state inside a per-tournament sequence. Validate duration and preserve the original start date on edits. Reconcile excluded members and counts when pre-start entry conditions change.                              |
| Team battles                 | Team-list updates could race registration or tournament start.                                                                                                                                 | Serialize team updates with other tournament mutations, read current state and update participant counts before invalidating caches.                                                                                                                                                                                     |
| Waiting/pairing              | A fast socket response could arrive before its waiting-user promise was registered. Stale waiting users could be paired while already playing.                                                 | Register the promise first; exclude database-confirmed active players from each pairing batch.                                                                                                                                                                                                                           |
| Interrupted pairing          | A crash between pairing insertion and game insertion, or a lost completion notification, could strand players. The WebSocket service excludes these players before reporting its waiting list. | Reconcile active pairings independently of that list at startup, periodically and before completion, using batched light primary game reads. Remove unstarted pairings with no game and process completed games through the normal result handler.                                                                       |
| Scoring                      | Duplicate finish notifications and cache loads racing completion could count a result twice. Partial score writes needed a safe retry.                                                         | Atomically finish a pairing once, make cached sheets idempotent by game ID, and recompute on duplicate completion retries without incrementing color history twice. Use actual played plies for short-draw and berserk eligibility.                                                                                      |
| Event completion             | Completion and game-result updates could race while choosing the winner.                                                                                                                       | Serialize tournament mutations and rebuild authoritative score sheets before selecting the final winner and publishing finished status. Games still running at the event boundary retain the normal Arena rule: they may finish but do not score.                                                                        |
| Reconnect                    | The in-memory current-game index was treated as authoritative after startup, so missing entries could hide the return-to-game link.                                                            | Fall back to the indexed active pairing lookup whenever the in-memory entry is absent.                                                                                                                                                                                                                                   |
| Pause                        | The initial pause record used a timestamp captured once at server startup.                                                                                                                     | Create a fresh timestamp for each player's first pause; a regression test checks a later player's full rejoin delay.                                                                                                                                                                                                     |
| Berserk and browser feedback | Server berserk handling did not fully validate the active event/pairing. Failed join/withdraw requests could leave a spinner stuck.                                                            | Validate event state, feature setting and exact current game; always clear pending browser state and refresh after join failure.                                                                                                                                                                                         |

The inherited pairing cadence, matching algorithm, per-player score-sheet cache, indexed persistence, and rule that unfinished games do not score were retained. Recovery batches small game projections approximately once a minute rather than scanning move histories or running on every move. The rehearsal engines run entirely on the operator machine.

The concurrency review also covers debounced participant counts, play-ban pauses, berserk acknowledgements, operator score recomputation and featuring changes. These operations use the same per-tournament sequence. Operator recomputation and removal of a finished participant invalidate cached rankings and page data so that historical standings do not remain stale for an hour. Changing an unused event's native variant also clears a custom position belonging to the previous variant.

A real browser game ending with only defensive material also threw “Expanded FEN expected to be 64 characters.” The shared result-status renderer still guessed Western-chess draw rules from the board. The obsolete material and 50-move inference has been removed; the renderer now uses the server's native adjudication reason through the shared Xiangqi presentation layer. Regression coverage includes Standard, Jieqi, Mini Xiangqi, repetition, no-capture, stalemate and agreed draws.

## Stored data and deployment

`tools/data_migration/20261029_tournament_variants.js` repairs unused legacy definitions that stored a Jieqi/Mini policy without native variant metadata. It validates the complete candidate set before mutation and retains original documents in `__tournament_variants_v1_backup`. It stops if a candidate has participants, game history or a custom position: those records require review because the old implementation may have created Standard games under a variant policy. Played history is never silently reinterpreted.

The adjacent `lixiangqi-beta-deployment` repository's `push-local-live.ps1` packages this migration and `push_transport.py` executes it while application writers are stopped. No deployment was performed.

## Verification

The audit uses a fresh, isolated local MongoDB database and local web/WebSocket services. No production snapshot was imported and no live rehearsal was run. The browser runner requires no backend testing hooks. Account creation and gameplay are performed through the visible site; local cleanup uses the separately approved operator command.

The complete browser rehearsal passed on 29 October 2026:

- Run `mvthgfdpd9d7`, local tournament `LjD4w1kw`: ten newly registered accounts, ten independent Chromium processes and ten local Pikafish engines.
- The configured 20-minute event reached its finished screen at `12:14:04 UTC`. All 25 games completed, with the final game ending at `12:16:05 UTC`; the browsers made 2,470 acknowledged moves.
- Independent score calculation matched all ten displayed score sheets. Twenty-one games counted, and four completed after the event cutoff without affecting the standings. The run included two draws and a valid berserk win bonus.
- Reload/reconnect, pause/rejoin and berserk all executed. Every account completed at least two games. Player browsers recorded zero uncaught JavaScript errors.

Headless Chromium was found to receive crawler/spectator pages, so the rehearsal now requires visible browsers locally as well as live.
