# Live puzzle publication

Puzzle Studio prepares content locally and publishes through the running LiXiangQi application. Production MongoDB is authoritative for published membership, author revisions, ratings, votes, and rounds. Ordinary website deployment contains no puzzle inventory or games database and does not install or restore puzzle collections.

## Operator workflow

1. For **Live Site** publishing, give the operator account `PuzzleCurator` permission and create an OAuth token with the dedicated `puzzle:publish` scope. Set `LIXIANGQI_PUZZLE_TOKEN` in the environment that launches Studio. Tokens are never saved in Studio settings, review documents, or logs.
2. Set the HTTPS publication origin in Settings. Auto Start reconciles the live inventory without stopping the website. Discovery, engine verification, solution construction, and classification use local databases and local engines. Existing verified local native-game snapshots can still be imported; Studio does not capture a production database to publish.
3. In Puzzle library, filter categories and the **New - Ready for Publication**, **Published**, or **Retired** pools. Output with a supported basic kill pattern or **Winning Material by Double Attack (捉双得子)** appears automatically. Mate-in-1 through mate-in-8 are auxiliary tags and never qualify alone. Publishing withdraws previously published puzzles that lack a supported category. Pipeline queues are not library pools. Published/Retired reflect the last downloaded server inventory; the Changes column shows local edits.
4. Select one or multiple puzzles and use **Withdraw**, **Reject**, **Edit tags**, or **Restore** below the list. Rejected new puzzles are excluded from publishing. Retired puzzles retain their content and identity.
5. Choose **Publish to Local Preview** (selected by default), **Publish to Live Site** (off by default), or both. Preview startup downloads and restores the snapshot, then provisions **testing123 / testing123** with admin and puzzle-curation permissions and a repeatable publishing token. Studio uses that token automatically for loopback preview destinations; there is no preview token or login prompt. The default address is `http://localhost:9663`. Live publishing uses `LIXIANGQI_PUZZLE_TOKEN` or prompts for a token kept only for the Studio session. Click **Publish** to sync all ready additions and local changes. There is no limit on the number of changes selected for a sync. The Publish progress bar shows cumulative changes for each destination, including progress resumed after a connection loss. Bounded API requests happen internally. Failures appear in Activity; requests and receipts are retained under Studio's state directory.

6. After a connection loss, click **Publish** again. Studio checks the interrupted batch's durable server receipt and recovers an accepted request unchanged. Unsent batches are archived and rebuilt after refreshing the server inventory. Server recovery continues while Studio is disconnected. A conflict downloads the full current inventory, retains local edits, and archives the remaining stale queue; inspect the library before publishing again. The next attempt builds fresh batches rather than trying the next stale batch. Activity reports preparation and comparison counts, server status, and elapsed time during waits. Fresh batches use a new progress total after recovery.

The environment token is checked by the normal server OAuth layer; both scope and curator permission are required. Redirects and non-loopback HTTP origins are refused by the client. Local HTTP requests bypass proxies. Preview has a separate catalog, outbox, and receipts under the Studio state directory; it never confirms changes in the live inventory. When both destinations are selected, each is attempted and failures are reported separately. MongoDB is never exposed to Studio.

## Completed game analysis publication

Discovery automatically uploads each completed game analysis to the configured Live Site. Start, Re-scan, and Auto Start request the existing session-only `puzzle:publish` token when needed. The command-line discovery script uses `--publication-origin` (default `https://lixiangqi.com`) and `LIXIANGQI_PUZZLE_TOKEN`, or a hidden token prompt in an interactive terminal. It checks access before starting engines. Preview selection in Publish does not redirect discovery uploads.

Each discovery worker saves the full analysis and its pending delivery atomically, then uploads independently. Multiple workers can upload simultaneously; no database transaction is held while waiting for the website. Transient upload failures receive two retries. A persistent failure stops the run with the analysis still saved; restarting Discovery retries pending uploads concurrently without rerunning engine analysis. Publish can also deliver pending analyses. Credentials are never written to the queue, settings, logs, or command arguments.

Publish also uploads discovery's completed full-game analyses to each selected destination, including games with no puzzle candidates. It selects the deepest retained completed run for each game and checks destination depths in batches of 100 before decompressing or uploading evidence. Interrupted, rejected, and partial discovery jobs are excluded. Catalog source aliases resolve to the canonical catalog game; native IDs stay tied to their production origin, including when publishing to a preview restored from that origin.

The application stores these results in the normal `analysis2` collection. A conditional write replaces an existing result only when the incoming depth is strictly greater. Depth is the minimum achieved search depth over the game's nonterminal positions, never the requested setting, engine version, timestamp, or node count. Equal and shallower results leave the existing analysis unchanged. Older server records without retained depth are preserved: their quality cannot be compared, so replacement could cause a downgrade. New Fishnet results now retain depth too. The unique analysis ID protects simultaneous publishers and late Fishnet results from overwriting deeper analysis.

Native publication verifies the complete move history and initial position, marks the game analysed, sends the normal analysis completion events, and removes queued or acquired Fishnet work. Retrying publication also repairs interrupted completion. Catalog results appear when their game is loaded in the analysis board, with the same score and variation projection. The progress bar reports the analysis phase separately from puzzle changes.

The curator API adds `POST /api/puzzle/publication/analysis/inventory` and `POST /api/puzzle/publication/analysis`, under the existing `puzzle:publish` scope and `PuzzleCurator` permission. Reads use `GET /api/analysis/catalog?id=...`. Native game analysis reads keep their existing routes. Each successful upload confirms the retained depth; fresh server inventory is the durable retry checkpoint, so resetting preview cannot leave a stale local uploaded flag.

No production migration or deployment step is required. The normal application/asset deployment includes the endpoint and viewer changes; `push-local-live` already fingerprints these inputs. Studio adds and backfills a local per-run depth index from the retained compressed evidence without changing that evidence.

## Studio pipeline numbers

The overview separates retained inventory from completed work:

- **Retained candidates** counts source positions, including positions not yet verified.
- **Categorizer pool** counts checkmate and tactic candidates with an accepted, complete current-policy solution. Categorized and uncategorized members remain here after every run.
- **Needs category updates** counts pool members missing a current category check or the resulting classification snapshot.
- **Ready to publish** and **Published** describe authored publication inventory, not categorizer input.

The Categorize card divides its pool into **current** and **needs updates**. Its
matched/unmatched counts describe current members only. **Category checks** counts
completed candidate/category pairs at the current versions, so its denominator is
pool size multiplied by category count. An inconclusive attempt remains retryable.
Adding a category increases required checks; changing a version invalidates only
that category's checks. Neither operation removes puzzles from the pool.

Discover reports source games scanned at the current discovery version. Separate
**Verify & construct checkmates**, **Categorize checkmates**, **Verify & construct
tactics**, and **Categorize tactics** cards each have their own Start/Stop buttons
and repeat controls. Each verifier reports eligible solutions for its candidate
type. The tactic categorizer detects `winningMaterialByDoubleAttack` and selects
the capture endpoint. Raw verification evidence is retained. Auto Start starts
discovery and all four evidence stages; worker settings apply per type. Worker
**Running/Stopped** reflects Studio's actual process state; historical database
claims are not shown as running work.

Normal **Start** performs incremental category work. **Force recheck…** deliberately
repeats same-version logic against the same eligible pool, using saved solutions
and engine evidence. **Audit published themes** is a separate frozen-release audit.

Scripts upgrade local mining storage to schema 16 transactionally, without an
automatic full-database backup. Opening Studio does not migrate or back up data.
Stop old workers before upgrading and restart Studio after updating.

views, installation, refresh behavior, and measured read latency.
Category endpoints are stored separately from immutable verifier evidence;

## API and ownership

- `POST /api/puzzle/publication`: `{operationId, digest, changes}`. Each change supplies `puzzle`, `expectedDigest`, `expectedRevision`, and `provenance`. New records use null preconditions and verified assessment provenance. Existing records require the exact inventory digest/revision.
- `GET /api/puzzle/publication/:id`: durable status (`submitted`, `applying`, `visible`, or `conflict`), progress, errors, and the original request.
- `GET /api/puzzle/publication/inventory?after=ID`: at most 100 authored records, revisions, and a publication version. Reads during publication conflict; clients must reject a paginated inventory whose version changes.

The shared puzzle module owns validation and publication. It rejects user-owned fields, duplicate IDs, missing source snapshots, malformed source/solution data, incompatible solve identities, stale revisions, and operation-ID reuse with a different digest. Identity comprises puzzle ID, source identity, FEN, and solution. A changed solve requires a new puzzle ID; retire the old content explicitly. Retired content remains addressable by direct ID and historical rounds.

Offline assessment application preserves the puzzle ID for category-only changes and reuses saved IDs when a previously withdrawn solve returns. Categorization carries completed categories and evidence into existing authored entries; local admission rejects a second ID for the same source game, FEN, and move line, including retired entries. The server check remains a final integrity boundary.

For local databases affected by the former category-only replacement bug, stop Studio workers and run the following from the repository root. The default is an inspection; add `--apply` to repair. It backs up both SQLite databases and the outbox under the state directory's `recovery/solve-identity-*` folder, preserves reconciled live IDs and assessment history, and removes redundant local publication rows. It archives and removes only outbox batches whose duplicate solve identities guarantee rejection before server journal admission; potentially accepted operations require receipt reconciliation. No live data or deployment migration is involved.

```powershell
.venv/Scripts/python.exe -m tools.data_migration.20260913_puzzle_solve_identity --database data/local/xiangqi-puzzle-mining.sqlite3 --catalog data/local/puzzle-catalog.sqlite3 --state-dir data/local/puzzle-studio
```

The repair is resumable. For recovery from a faulty repair, stop Studio and restore both database backups from the same recovery directory (including removal of their stale SQLite WAL/SHM sidecars); retain the archived outbox for inspection before resuming publication. Restart Studio after updating its Python tools.

Canonical JSON sorts object keys, preserves array order and Unicode, and writes finite numbers in plain decimal form without insignificant zeroes. SHA-256 covers `{changes}` for requests and normalized authored content for puzzle digests. `retirementReason` is normalized to null when absent. Author revisions also guard against an ABA change that restores an earlier digest.

Publication only changes authored fields and their ownership metadata. Ratings, plays, vote totals, daily dates, moderation flags, rounds, and source user profiles are not restored or replaced. Effective themes combine `managedThemes` with `communityThemes`. The theme-vote projection and tagger preserve this ownership. Theme writers use a vote generation and author revision when denormalizing so neither concurrent votes nor publication are erased by a stale projection.

## Journal and recovery

`puzzle2_publication` contains permanent requests/receipts and a singleton control record. The control record serializes publication across application processes. There is no expiring lease that can authorize a second publisher underneath a suspended worker. Workers may replay the same operation safely using revision checks and guarded phase changes.

The entire batch is validated before any puzzle is changed. Its plan stores the previous authored content durably before application. Content, journal, and selection writes use majority acknowledgment with journaling. A database error leaves the operation recoverable; a semantic conflict before application is terminal. A crash during application resumes forward. Do not reset the control record or restore an old puzzle database snapshot to recover a publication: that would lose newer user activity. To undo an editorial mistake, review a new operation using current revisions and the retained previous authored content.

Application startup polls the journal, including work left by a previous process. A disconnected client may query its receipt or resubmit its exact request. Completion is recorded before releasing the control record. Receipts are not expired.

## Selection and visibility

Publication retains the existing small-catalog rating-banded paths. It rebuilds only the affected angles (including mix), reading a compact ID/rating/theme projection rather than source snapshots or user histories. Rebuilding mix still requires reading and sorting the active inventory. No engines run on the server.

Each path-build attempt uses distinct immutable generation IDs. After all pages are durably written, the winning generation map is recorded in the journal; one atomic control-document update activates it. Interrupted and competing attempts cannot mix pages. Existing sessions retain their old immutable path positions. All training lookups check current retirement and theme eligibility. An already-issued puzzle can still be completed normally after retirement.

`visible` means authored writes and selection activation have completed. Theme counts use a cache keyed by the publication version, so an old in-flight count load cannot conceal a new publication. Anonymous pools expire within one minute and revalidate active IDs on each response. Daily results likewise revalidate active membership before serving cached HTML; the next daily lookup replaces a retired daily. Thus cached pools may delay additions for up to one minute but cannot indefinitely serve retired content. Requests already in flight can finish with the previously issued puzzle.

The application also schedules hourly path refresh through the same journal to follow live rating and community-theme changes. Superseded generated paths are collected after two days; sessions expire after one hour, and historical playback does not depend on paths. The former collection-replacing path cron and offline content installer have been removed. Do not run copies of those retired programs against production.

## Deployment and preview

The test-account bootstrap is restricted to the fixed `lixiangqi_preview` database. It uses the application's compiled password hasher, preserves previous account/token documents under `data/local/preview-account-backups`, and runs after snapshot restoration on every preview startup. It does not provision accounts in production. The documented test password and token are public preview fixtures.

The first deployment requires `tools/data_migration/20260912_puzzle_publication_v1.py`. The September 12 live audit found that all 108 installed puzzles lacked source snapshots, retirement fields, and theme ownership. With writers stopped, deployment resolves missing snapshots from the server-owned catalog or native games, validates the entire inventory, retains immutable original MongoDB documents and per-record plans, adds only missing metadata, and verifies preservation before startup. It does not publish, retire, relabel, replace, or delete puzzles. Interrupted migration resumes from the retained plans; code rollback completes additive metadata before allowing old writers to resume. Existing unversioned selection pages remain readable until the application generates replacements. New publication indexes and the control record are initialized idempotently by the server.

`push-local-live.ps1` and its transport reject data files in application payloads. The transport moves the existing server `data` directory once to a stable sibling `<remote>-data` directory and links application releases to it. Rollout and rollback never install or restore puzzle inventories; only the explicit additive migration changes existing puzzle documents. Other existing application migrations retain their own backup/recovery mechanisms.

Disposable preview still restores verified production snapshots with recoverable local backups. Older production exports can lack required puzzle source snapshots. Preview preparation resolves those sources from the local games database, validates the entire inventory before writing, and fills missing required fields only in `lixiangqi_preview`. It preserves IDs, themes, ratings, plays, and user history; it never overlays an authored release. The immutable production archive retains the original documents, and restarting preview restores that archive before preparation. A missing source game fails startup with the puzzle ID. This local preparation does not migrate production data. Full production snapshot capture is a separate, online environment-data operation. It never stops live services or locks out writes. MongoDB performs a full `mongodump --oplog`; an isolated temporary MongoDB replays that log before producing all three canonical snapshot files. The temporary server uses the production MongoDB image, has no network or production volumes, and disables TTL deletion. Capture/replay errors (including oplog rollover or unsupported concurrent schema changes) fail preview startup rather than publish an inconsistent snapshot. A captured pending puzzle publication also fails; retry after publication completes. The deployment lock excludes deployment/migrations during capture, while normal gameplay and puzzle solving continue. Downloads read the completed immutable files.

Online capture requires the single-node `lixiangqi` replica set. `push-local-live` enables it during the existing deployment maintenance gate, retaining a full pre-conversion archive and checksum under `/opt/lixiangqi-beta-mongo-replica-backups/`. Interrupted initialization resumes on deployment retry or recovery. This is a one-time deployment prerequisite, never an action performed by preview startup. Until deployed, preview reports the prerequisite and leaves the live site running. A point-in-time database copy can still contain an application operation between separate, nontransactional writes; oplog replay prevents discrepancies introduced by the duration of the copy, not transient states already present in production.
